# 起因

作为一个后端开发，排查线上问题最直观的就是看日志，以往打开日志文件都是用sublime等文本工具打开看，直接搜一下报错的内容或者log提示信息定位位置。
不过，不知道大家有没有相同的困惑：
1. 可能报错的内容不止一个地方，不停点【next】，日志时间就不知道飞到哪儿去了。不能聚焦于某个时间段的日志上下文。
2. 并发高或者遇到多线程任务时，不同线程的日志会交错在一起，看起来眼花缭乱。

为了解决这两个问题，我打算自己做一个方便看日志文件的应用。


# 开动

有了想法，就要付诸行动。目前我们只有两个痛点，一个是时间难找，一个是不能只看某个线程的日志上下文。其实都不难，只需要解析一下日志内容就可以了。
不过除了我的需求之外，还有个巨大问题，如果一份日志文件有几个G的大小，那么全部读到内存里不是全炸了？所以开发的技术选型语言上面需要斟酌一下，现在在AI的赋能下，哪怕我真的不会，想要实现这样的功能也没有太大的难度。

几个语言的对比：

|对比项|Rust|Java|Go|
|---|---|---|---|
|大文件索引|可用紧凑的结构体存储事件。LogScope 当前每条索引记录约 40 字节|可用基本类型数组或字节缓冲区实现紧凑索引|可用结构体切片实现紧凑索引|
|内存管理|编译器检查所有权和借用，运行时无需 GC|JVM 管理内存和垃圾回收|Go 运行时管理内存和垃圾回收|
|桌面分发|核心直接编入 Tauri 应用|常规 JVM 方案需要随包提供 Java 运行时，或依赖用户已安装的环境|可编译成独立的可执行文件|
|接入现有 Tauri 后端|CLI 和桌面端直接依赖同一个 `logscope-core`|需要跨语言调用，或把核心作为独立进程接入|需要跨语言绑定，或把核心作为独立进程接入|
​
对 **LogScope** 来说，更有意义的是**读完以后，能给多少条事件建索引**。Rust 可以做到每条基础索引约占 40 字节，虽然Java 和 Go 也能用紧凑的数据结构实现同样的方案。但是最终选 Rust 的实际优势，是能直接控制索引的内存布局，并让 CLI 和 Tauri 桌面端复用同一个核心库。


# 功能

这是LogScope的主页面，左上角可以导入某个日志文件，刚导入时，会根据日志文件的每行内容进行解析，这个解析速度会很快。解析完成后构建顶部的时间轴，时间轴范围是整份日志文件的起始时间和结束时间。
![时间轴](https://raw.githubusercontent.com/CatMaiV/BlogImage/main/img/20261124152712366.png)
同时，时间轴上也会显著标识有error的日志，error日志是红色的，可以直观的看到在哪些时间上error突然暴增了。

时间轴上方是一些很基础的查询功能，包括日志级别的筛选，可以多选，只查看部分级别的日志。
![日志查询](https://raw.githubusercontent.com/CatMaiV/BlogImage/main/img/20261124152852065.png)

同时，在时间轴中通过鼠标选中拖拽可以快速聚焦某段时间内的事件。
![时间快速检索](https://raw.githubusercontent.com/CatMaiV/BlogImage/main/img/20261124153030249.png)

选中时间之后，日志列表就只会展现当前时间段的日志了。
![日志选中](https://raw.githubusercontent.com/CatMaiV/BlogImage/main/img/20261124151749946.png)

点击日志中的某一行，界面下方会出现事件详情的部分，事件详情可以根据同线程或日志文件的物理顺序展现当时的现场。
![事件详情](https://raw.githubusercontent.com/CatMaiV/BlogImage/main/img/20261124153319576.png)

以上就是LogScope的全部功能，其实功能很简单。至于LogScope能处理多大的日志，目前测到了1GB，再大的我还没试过。
**Rust 分块读取日志时，文件可以远大于内存。LogScope 当前能导入多大，主要取决于日志里有多少条事件，以及机器有多少可用内存。**

- **只读取文件**：Rust 的文件定位接口使用 `u64` 字节偏移，理论上能表示接近 **16 EiB** 的偏移。实际单文件大小由操作系统和文件系统决定。例如，Windows 上使用默认 4 KB 簇的 NTFS，单文件上限约为 **16 TB**。[Rust 文件定位文档](https://doc.rust-lang.org/std/io/enum.SeekFrom.html#variant.Start) · [微软 NTFS 上限说明](https://learn.microsoft.com/en-us/windows-server/storage/file-server/ntfs-overview#support-for-large-volumes)
- **导入 LogScope 并建立索引**：原文分块读取，每条事件的基础索引约占 **40 字节**。按现有测试日志的事件密度估算，**10 GB** 日志的基础索引约占 **3.3 GB**，排序和查询还需要额外内存。代码里的单文件事件序号是 `u32`，约 **43 亿条事件**时会溢出。

**LogScope 在 CLI 基准测试中，扫描、解析并索引了 1 GB、约 828 万条事件的日志，耗时 13.8 秒，峰值内存约 473 MB。** 10 GB 是按事件密度推算的规模，目前没有对应的实测数据。
